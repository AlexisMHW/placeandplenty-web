## DEFECTS (not fixed, per instructions)

### DEF-1 (medium): an open dispute followed by the webhook's sweep permanently REVERSES the commission; a later "dispute won" does not release it
Repro (`e2e_verify/g_defects.mjs`, check DEF-1): purchase with a referred buyer, paid referrals ON. `apply_payment_event(dispute_opened)` then `sweep_commissions()` -> commission becomes `reversed / refund_or_dispute` (expected `held / dispute_open`). Then `dispute_won` -> entitlement is active again but the commission stays `reversed`.
Root cause: the payment ledger sets `gathering_entitlements.revoked_at` with `revoked_reason='dispute_open'` while a dispute is open; step 1 of `sweep_commissions` (217300) reverses every commission whose entitlement has `revoked_at` set unless `revoked_reason='subscription_deleted'`; the held/released logic (step 2) never gets to run, and reversal is terminal. Reached whenever a sweep runs while a dispute is open: the webhook runs one right after every dispute event when HC_LEDGER_WIRING_ENABLED=true, and the scheduled maintenance job does too. Seen in the webhook run: a Gathering Pass with dispute open then WON (entitlement active/paid) has a reversed commission; a Plus charge with dispute won then partial refund also ended reversed. Impact: the affiliate is underpaid (never overpaid); the founder rule "disputed excluded" holds but "won -> released" does not. Suggested direction (not applied): exclude `revoked_reason='dispute_open'` from the reversal predicate.
Note: the earlier scenario C10 (direct `record_purchase_dispute` calls without a sweep in between) passes; the defect only appears with the sweep, i.e. exactly the production wiring.

### DEF-2 (medium): a PARTIAL refund never holds the commission when driven by the webhook; it auto-validates and becomes payable
Repro (`g_defects.mjs`, DEF-2): `charge.refunded` with `amount_refunded < amount` -> ledger marks `partially_refunded`; the webhook plan for `refund` is `reconcile_commission_for_entitlement` (+ sweep). Commission stays `pending`; `sweep_commissions(now()+46d)` -> `validated`. Expected (founder rule, C15, comments in hcLedger.ts): `held / partial_refund_review`.
Root cause: `record_purchase_partial_refund` (214003 / 217440) exists and works (C15 passes when it is called) but nothing calls it: not `handler.ts`, not `hcLedger.ts` (`partial` is computed in `hcAfterLifecycle` and then ignored), not the web planner. Webhook result/entitlement are unaffected (partial refund still reports `partial_refund_flagged`, access kept).

## Observations (not failures)
- O1 (policy question for the founder): `hc_create_payout_draft` and `hc_activate/deactivate_paid_referrals` use the plain hc.payout rule, not owner-only (217430 header says so deliberately). Today only `owner` holds hc.payout, so nothing is exposed; if hc.payout is ever granted to another role (C-O1 modelled this) that role could create drafts and flip the paid-referral switch at the DB, though the web UI is owner-only for all of it (C-W2). The "owner-only" wording applies to approve/record/void/reverse/settle.
- O2: when the paid-referral switch is OFF, `reconcile` answers `paid_referrals_disabled` even for a purchase made inside an earlier ON window; accrual is deferred until the next activation (then picked up by maintenance, B-W9), not lost.
- O3: `hc_commission_maintenance` only looks back 30 days (`p_lookback_days`), so a purchase made in an ON window and reconciled after the switch was OFF for more than 30 days would not be picked up.
- O4: ts217400 W8.7/W8.9 fail only because Supabase's default privileges give `service_role` ALL on new public tables and the migration does not revoke insert/update/delete from it; the append-only triggers still block update/delete, and an insert is stopped by the one-open-window unique index. Same in real Supabase, so the claimed "service role cannot write" is not strictly true (service role is trusted).
- O5: server timezone matters for `hc_record_external_payment` ("future date" uses the DB date). On a non-UTC server the UTC "today" is rejected in the evening; Supabase runs UTC, scratch was pinned to UTC.
- PARTIALs carried from the old harness unchanged: A13 (approve applicant without an account), A14c (member suspension raises no inbox row), C1c (now shows `not_qualifying_paid_referrals_off_at_purchase`, i.e. the old retroactive observation is resolved), C4a (claim grace 24h), E1b (photo exception on completed; fixture lacked storage_path, now covered by E-2/E-4), E7 (cancel on a completed gathering is refused), F1 (1 unclassified function: `get_multi_day_lock_in_gate`), F4.
